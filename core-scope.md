# KEPVY: core scope C01–C14

Status: reconciled requirements, not implemented  
Date: 2026-10-14  
Confirmed decisions: the complete core for KAY, one team, French interface, MAD, and `Africa/Casablanca`.  
Technical proposals: mechanisms in the [data model](docs/04-design/data-model.md), [architecture](docs/04-design/architecture.md), and [API](docs/04-design/api-contracts.md).  
References: [product brief](Project-brief.md), [business rules](docs/02-requirements/business-rules.md), [tests](docs/05-quality/acceptance-tests.md), [lifecycle guide](software_engineering_lifecycle.md).

The C identifiers are stable. Completing a module requires evidence of permitted behavior, denial, and recovery. The [traceability matrix](docs/05-quality/traceability.md) lists scoped SP-01-SP-04 local evidence. The later full-product business, file, load and recovery scenarios remain unimplemented/unverified; an identity test is not whole-core acceptance.

| ID | Expected outcome and limits |
|---|---|
| C01 | First administrator created once by an interactive script run on the deployed server by that intended administrator; subsequent accounts created manually by an administrator. `administrator`, `manager`, and `agent` roles; email/password sign-in; proposed in-person temporary-credential handoff, pending state, and required first-login change for later staff; revocable seven-day session; another user's password reset requires the administrator's password and revokes the target's sessions. No MFA, SMTP, email verification, invitation, or public sign-up. |
| C02 | Contact with required name and phone, multiple phones/emails with primary values, selected international calling codes, residence/nationality and multiple spoken languages; one canonical contact per normalized phone. Under D35, manual Leads require client languages and budget and expose campaign source/rating separately from immutable received provenance. Legacy/imported/website unknown profile facts are retained without fabrication. Separate enquiries; duplicate warning and resolution within the user's scope; another agent's private contact blocks creation and shows only its responsible agent. Primary agent, collaborators, and assignment history. |
| C03 | Multiple purchase/rental requirements, MAD budget, required/preferred/unknown criteria, filters, and manual shortlist of exact physical-unit or whole-development offerings; monthly and yearly rents compared exactly on a twelve-month basis. |
| C04 | Villas, houses, apartments, and land parcels as standalone assets or units in a development. Apartment developments have one or more blocks, floors, and physical units; other/mixed developments may omit blocks and floors. A development-scoped unit type is a reusable template, never the transactable unit. Physical units and whole developments may each have distinct sale/rental offerings, with overlap checks; one active reservation per offering without automatic expiry. A development may have an optional shared project briefing. All active staff may create/edit shared project facts, hierarchy, types and properties/units (D34); legal owners, inventory-file writes, offerings/availability, external stock outcomes and archive/restore remain M/A-only. Shared inventory attachments are readable by all agents. Developer/owner private data stays on protected contact records. |
| C05 | Contact timeline with the true actor, notes, manually logged interactions, and assignment history; access follows current scope, and history is not rewritten. |
| C06 | Tasks, due dates, internal notifications, and overdue lists; deduplicated reminders invalidated on reschedule or completion. |
| C07 | `company_car`, `without_company_car`, and `office` visits with participants, duration, location, confirmation, rescheduling, and outcome. Both off-site types follow administrator-configured working days/hours and lunch breaks; office visits may occur at any time. Company-car visits have an agency-wide, administrator-configurable hourly cap initially set to two. Conflicts trigger a warning and require a reason for confirmation; colleagues see only free/busy. |
| C08 | Multiple deals per contact. D35 adds explicit versioned Lead conversion requiring project, budget and buying intent, with inherited canonical client/source and an automatically derived display title. Manual qualified deals use an existing or atomically created client, known languages and one to three project interests; project interest does not reserve stock. The fixed pipeline retains skippable stages, separate customer offers, reservations, and closing with amount/date/explanation; primary agents and collaborators may reopen, subject to stock checks, with competing deals flagged. |
| C09 | Optional fixed or percentage commission; recognition and collections limited to managers/administrators; partial receipts, rejected over-collection, and corrections that preserve the original. No banking, payroll, or official accounting. |
| C10 | Portfolio KPIs by current primary agent, outcomes by primary agent at close, activity by true actor; explicit definitions and periods, scope-filtered data; separate counts for developments, physical assets/units, and offering levels; 30-day inventory and 14-day inactive-deal alerts. |
| C11 | Search/filter developments and physical units by hierarchy, category, type, and offering level with numbered pages and Next/Previous; fixed-template **contact** CSV, managers/administrators only, agent indicated per row, existing phones skipped, invalid rows corrected before approval, atomic commit; controlled export. This does not authorize inventory CSV import. |
| C12 | Contract for one existing website form, authenticated source, durable and idempotent intake, and reuse of known contacts. Identify the actual site before connecting it. |
| C13 | Responsive French web app on desktop, tablet, and phone; login first, then a role-scoped dashboard and left navigation for Dashboard, Leads, Deals, Visit Calendar, Projects, and Settings. Leads are enquiries linked to contacts. Lead and deal lists support search, filters, numbered pages, and configurable visible columns without changing authorization; project lists are searchable/filterable with numbered pages. Loading, empty, error, denied, and conflict states; keyboard, touch, and zoom. The named-screen inventory is in the [screen map](docs/04-design/screen-map.md); the actual route count follows the approved local placements. No native app or offline synchronization. |
| C14 | Server-side authorization, audit, controlled private files, recoverable archiving, consistent backups, and tested restore; two-year security audit retention, with a separate transaction policy still requiring confirmation. |

D29 selects H-01/H-02/H-03 as local defaults (positive price, recorded legal owner and multiple owners); later real-use validation remains in [decisions](decisions.md). The [22-sprint local roadmap](docs/03-planning/sprints/README.md) excludes deployment/cloud provisioning and implements the full local core with real local services and isolated tests. The [O01–O23 catalogue](Project-brief.md#future-catalogue-outside-the-core-o01o23) is outside this release **except O17**, which KAY promoted into C04. Adding any other option requires an explicit scope change and updates to permissions, data, and tests before development.
